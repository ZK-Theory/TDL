#### B-2 — The `computational_log_entry` anchor does not fit the Computational-Log it governs.

**Location:** segmentation contract §3 table, row `computational_log_entry`; §4.5.

**Claim.** The anchor is "a level-3 heading `### YYYY-MM-DD -- `", over "the whole page".

**Evidence.** From the live page at 2026-10-23T08:22:53Z (SHA-256 `de44a67b…`):
- **Heading forms.** There are 255 level-3 headings. Only 201 match the anchor.
- **Legacy period** (dated on or before 2026-07-18, the W9 §7.3 cut). 114 headings match. Another 47 dated level-3
  headings do not match:
  - double-encoded em dashes (for example L4440 `### 2026-06-02 Ã…`);
  - `(canonically backfilled 2026-06-01)`;
  - `(later)`;
  - ` - ` (L4664);
  - `2026-06-03b` and `2026-06-03c` (L4271, L4247);
  - `~2026-…`;
  - ` ? `.
- **Level-2 entries.** Six dated level-2 entries exist (L5594, L5611, L5628, L5668, L5697, L5723).
- **The template disagrees too.** The filing template in `.claude/rules/vault-templates.md:20` is
  `### YYYY-MM-DD — PXX:`, with an em dash, not `--`.
- **Absorption.** The page's level-1 title `# Computational Log` sits at L4436, inside the span region of the anchor
  at L4429. The six level-2 entries also fall inside preceding level-3 spans. Neither the rule "the whole page" nor
  "next anchor of the same kind" stops at them.
- **Separators.** 175 of the 201 matching entries end with a `---` rule line. That separator becomes part of the
  entry's hash. D8c treated `---` rules as structural.
- **Blockers.** §4.5 makes a line that "looks like an anchor … but does not parse" a blocker. "Looks like" is not
  defined. One implementation will block all 53 non-matching legacy-period headings. Another will treat them as body
  text and fold them into the previous entry. Both readings are literal, and their spans and hashes differ.

**Failure scenario.** Under D-7 the contract is accepted together with the L-0b export, and the export is the only
baseline that can ever exist (W9 §7.3 item 6: "the vault has no history").
- About a third of the legacy-period entries (53 of 167 dated headings) either become blockers or are silently merged
  into a neighbour's hash.
- The page title and the six level-2 entries are hashed as part of unrelated entries.
- Two independent exporters disagree.

**Impact.** Validity of the one irreplaceable baseline, and of W9-T19.

**Required change.** Derive the anchor grammar from a census of the actual page, committed with the contract.
1. Define the anchor as a heading line of level 2 or 3 whose text starts with a date token. Give the token grammar
   explicitly: `~?YYYY-MM-DD` with an optional `[a-z]` or `/DD` suffix and an optional parenthetical. Make the
   separator irrelevant to anchoring.
2. End every entry at the next heading of level ≤ 3 that is not an anchor, or classify such headings as structural.
3. State whether trailing `---` rules belong to the entry. Recommendation: structural, to match D8c.
4. Define "looks like an anchor" as a closed rule; for example, any level-2 or level-3 heading starting with a digit
   that fails the grammar.
5. Record that the anchor text is the raw heading bytes, mojibake included. It is never decoded or repaired.

**Affects:** D-7, L-0b, O-21, W9 §7.3, W9-T19, WP9.3.

#### B-3 — The tracker selectors do not fit `.apm/tracker.md`.

**Location:** segmentation contract §3, rows `working_note_entry` and `tracker_task_row`.

**Claim.**
- `working_note_entry` is anchored on "a date heading (`### YYYY-MM-DD` or the file's own date-heading form, named in

- `tracker_task_row` is a row whose "first cell, trimmed of spaces, equals a task ID".

**Evidence.** From `.apm/tracker.md` at `HEAD` (blob `e791d95d`):

  2026-06-22 and 2026-06-20 head six each.
- **W9 already said so.** W9 §5.5 defines the entry as running "from the entry's **bullet** or heading to the next".
  The contract drops the bullet form, which is the only form present.
- **The escape hatch moves the grammar to the inventory author.** "The file's own date-heading form, named in the
  inventory" lets each inventory author choose the grammar. That defeats the contract's purpose (§1: "every observer
  cuts the item at the same bytes").
- **The anchor text is undefined for a bullet.** If it is the date, the 22 repeated dates are all duplicate-anchor
  blockers (W9 §5.5) and closure can never pass W9-T18. If it is the whole first line, the duplicates mostly vanish.
  The contract does not say which.
- **Task cells are bare numbers.** The first cells are `0.1`, `1.37`, `1.2g`, `1.15a-redo` and similar. They are not
  `T1.37`, the form W9 and every governing record use. No mapping is stated.
- **Other rows share the tables' shape.** The same section holds:
  - repeated header rows `| Task | Status |` (L11, L33, L70);
  - separator rows;
  - an "Open threads" table whose first cells read `T1.20 parental-NS-SEC audit` (L65);
  - Worker Tracking and Version Control tables (first cells `panel-statistics-agent`, which appears twice, and
    `` `c:\Users\steph\TDL` ``).

  The contract names no task-ID grammar and no covered region, so whether these are unaddressed blockers, ignored, or
  duplicates depends on the implementation.

**Failure scenario.** Two inventory builders produce different item sets for the Working Notes, or one produces
none. A tracker closure (W9-T18 bijection) is then either impossible or depends on the builder.

**Impact.** Validity of W9-T18 and W9-T22. Operations: the closure of the primary APM coordination file.

**Required change.**
1. Specify the Working Notes anchor as a top-level bullet line (`- ` at column 0) inside `## Working Notes`.
2. Give an explicit date grammar for dated entries.
3. Decide how undated top-level bullets are handled: each is its own item, anchored by its own line hash, or they are
   classified blockers.
4. Make the anchor text the full first line, without its terminator, so that same-date entries are not duplicates.
   W9 §5.5's example, "two Working Notes under one date heading", then needs a one-line reconciliation note, because
   the file has no date headings.
5. For task rows, fix the grammar of the first cell (for example `[0-9]+\.[0-9]+[a-z]*(-[a-z]+)?`) and its mapping to
   the `T`-prefixed ID.
6. Restrict the covered region to the stage tables under `## Task Tracking`.
7. Classify header and separator rows as structural.
8. State that rows of other tables are out of region.

**Affects:** O-20, W9 §5.5, W9-T18, W9-T22, WP9.3.

#### M-4 — "Terminator" is undefined, which splits CRLF and BOM files.

**Location:** segmentation contract §2.2, §2.4, §3 (the `heading_section` anchor text; `log_frontmatter`).

**Evidence.** §2.2 says the CR before an LF "belongs to the line", but never says whether the terminator is `LF` or
`CRLF`. §2.4 (a blank line is its bytes "minus its terminator") and the anchor text ("without its terminator") both
depend on that. Under the LF-only reading:
- every CRLF blank line holds `\r` and is not blank;
- every CRLF anchor text ends in `\r`;
- `---\r\n` is not "exactly `---` plus its terminator".

The CRLF-terminator reading gives the opposite on all three. Real files are affected: of the 85 stage logs, 10 are
CRLF and 9 start with a UTF-8 BOM (8 with CRLF, 1 with LF). With a BOM, the first line is `EF BB BF 2D 2D 2D …`, which
is not "exactly `---`", so the `log_frontmatter` selector finds nothing in 9 files. The contract records the BOM
(§2.5) but does not say how it affects anchoring.

**Required change.**
- Define the terminator as `CRLF` when the LF is preceded by CR, otherwise `LF`. Apply that definition to blankness,
  anchor text and delimiter tests.
- State that a leading BOM is part of line 1's bytes for hashing but is ignored for anchor matching on line 1. The
  alternative is to make it a declared blocker. Either way, state it.
- Add CRLF blank lines and a BOM-led frontmatter to the reference vectors (m-7).

#### M-5 — The contract never says whether it is line-based or Markdown-aware.

**Location:** segmentation contract §3 (`heading_section` anchor and region; bullets; paragraphs).

**Evidence.** The anchor is "a line starting with `#`×k plus one space". The contract does not say whether:
- a `#` line inside a fenced code block is an anchor. The fence at Computational-Log L2231–L2240 has none today, but
  vault notes commonly do;
- setext headings (a text line underlined by `===` or `---`) are headings. The `---` lines in these files make this
  live;
- ATX variants count: up to three leading spaces, a tab after the hashes, or closing `#` sequences (closing hashes
  would otherwise enter the anchor text);
- a GFM table's first cell is split on unescaped `|` only. Tracker L82 has `B\|C` in a later cell.

An implementer using a CommonMark parser and one using line regexes produce different spans.

**Required change.** Add a §2.6, "No Markdown parsing". Segmentation is purely line-based: fences, setext headings
and HTML are not recognized; only the stated ATX form at column 0 is a heading. Then list which of these each
selector's reference vectors must cover. If fence-awareness is wanted, specify the fence grammar exactly instead.

**Location:** segmentation contract §3, row `conventions_unit`.

**Evidence.** Census of `CONVENTIONS.md` at `4b143c92` (575 lines, 10 `## ` sections, no `###`):

- **The footer.** The trailing `*Last updated: 2026-07-16*` (L575) is inside the last section, "Computational

- **Base indent and paragraph ends.** The section's "base indent" is not defined, though the file has 56 column-0
  bullets and 4 nested bullets at indent 2. A paragraph's end condition is not stated: it "runs to its last non-blank

- **Tables.** The 9-line table in "Computational Environment" becomes one paragraph unit. That should be stated, not

**Required change.**
1. List the structural lines explicitly: thematic breaks, the `*Last updated…*` footer, and the H1 plus blockquote

2. Define base indent as column 0.
3. Define a paragraph as a maximal run of non-blank, non-bullet, non-heading, non-structural lines.
4. State that a table is one unit.

#### M-9 — Container membership can carry a superseded subtree.

**Location:** membership template §3.1 ("List the containers … explicitly").

**Evidence.** In `usoc_headline_frozen_2026-05-28.json` (45 pointers, no arrays) the container `/result/h1` holds
both H₁ W₂ fields, which W9 §6.2 calls `superseded`, and `landscape_*` fields. The template assigns each container to
exactly one family but never says what that assignment imports. If membership of `/result/h1` or `/result` means "the
subtree", importing that family carries the superseded H₁ W₂ values. Preventing that is the whole purpose of W9 §6.2.

**Required change.** State that a container pointer's membership covers only the node's own shape (its key set or
length), never its descendants' values. Import is the union of leaf pointers in the selected families. List the root
pointer `""` explicitly.

#### M-10 — The array rule is not RFC 6901 and contradicts itself.

**Location:** membership template §3.4 and §3.5.

**Evidence.**
- §3.5 requires RFC 6901, which has no wildcard. `*` is a legal key character, so `/cells/*/h1_w2` is ambiguous with a
  literal key named `*`.
- §3.4 says a homogeneous array is "assigned as a whole", yet its example assigns one field across elements.
- "Homogeneous" is undefined. The T1.3 file has two arrays (`/per_dataset/{usoc,bhps}/significant_regimes`); the
  template gives no test for deciding whether they qualify.

**Required change.**
1. Define a separate pattern grammar: an RFC 6901 pointer in which a reserved token, for example a segment exactly
   `[*]`, means "every index of this array". State that it never matches object keys.
2. Define homogeneity as all elements sharing one pointer set relative to the element.
3. State that the importer expands patterns against the observed bytes, and that any expanded pointer outside the
   table is `unassigned`.

#### M-11 — The template hashes itself and binds an observation that does not exist yet.
