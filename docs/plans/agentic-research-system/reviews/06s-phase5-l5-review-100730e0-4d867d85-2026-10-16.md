### F1. Minor. The new primary-checkout guard also covers the durable checkout, and L6 does not name its fast-forward command

- **Contract:** runbook §3 L6 ("Fast-forward the checkout's `main` to `M2`"); P-058 P5-5.
- **Where at M2:** `.claude/hooks/commit_state_guard.py:106` (`PRIMARY_MOVERS`), `:437` (`primary_branch`) and
  `:535` (the deny loop).
- **Reachable path:** `primary_branch()` treats **any** non-linked checkout whose HEAD is `main` or `master` as
  "the primary checkout". `C:/Users/steph/TDL-ARS-G6-Checkout` is exactly that: a non-linked clone on `main`.
  Suppose a Claude Code session performs L6's fast-forward as `git reset --hard <M2>`, `git checkout <M2>`,
  `git switch …` or `git rebase …`. The hook then denies it with the message "…is the primary checkout…". An
  operator could misread that as a problem with the checkout. `git merge --ff-only` and `git pull --ff-only` are
  not in `PRIMARY_MOVERS` and pass.
- **Evidence:** code reading. The hook's own docstring and comment say "the primary checkout" (`C:\Users\steph\TDL`),
  but the predicate is structural.
- **Severity reasoning:** it fails closed. It cannot corrupt the store or bypass an authority gate. Codex sessions
  and the owner's own terminal are not subject to the hook at all.
- **Proposed disposition:** name the exact L6 command in the runbook, for example
  `git -C C:/Users/steph/TDL-ARS-G6-Checkout fetch origin` and then
  `git -C C:/Users/steph/TDL-ARS-G6-Checkout merge --ff-only 4d867d85574dcf90300f059ab1fd52324be3c85a`. Verify that
  HEAD is `main` at M2 and that the status is empty. Separately, log an observation that the guard's scope is wider
  than its name. Do not change the hook before L6.
- **Confidence:** high on the behaviour; whether L6 hits it depends on how the operator writes the command.
