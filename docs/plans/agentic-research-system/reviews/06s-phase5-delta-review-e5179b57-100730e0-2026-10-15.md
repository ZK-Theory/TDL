### 2.1 B-1 in detail

- **Reserve, re-pin, init give the pinned identity and digest.** Init consumes the reservation only through
  `_require_witness_matches_request` (`authority.py:1673`) and the reserved branch of `_write_identity`
  (`authority.py:1182-1198`). Together they bind the project, bootstrap hash, control root, code roots, schema
  root and schema-binding version. `load_store_origin_witness` checks the witness bytes against the committed
  digest. The binding test asserts `initialized.store_identity == reserved.store_identity`, equal digests, and
  that no stage is left.
- **Can a reservation be consumed twice, or by a different bootstrap?** No.
  - A different bootstrap, control root or code root is refused (`ConflictError`, "does not match initializer
    request").
  - Re-running reserve before init re-derives the same manifest and witness from the reserved stage, so the
    digest is idempotent.
  - Reserve refuses once a store is published (`authority.py:1686-1687`) or once a complete stage exists
    (`1724-1725`).
  - A second `store init` after publication only verifies the existing store (`authority.py:1688-1710`). It
    consumes nothing.
- **Does a partial reserve leave a state that `init` misreads?** No.
  - A crash before the witness is persisted leaves an orphan stage. `_matching_reserved_stage` skips it because
    its physical identity differs from any witness. The runbook's L3 check ("one stage") would show it.
  - A crash after the witness, or a foundation-output failure (the file is published after the reservation,
    `cli.py:356`), is recovered by re-running reserve, which gives the same digest.
  - Without the re-pin, init refuses before any write. That is B-1's own premise, re-asserted by the binding
    test.
- **B-1(c).** No store binding exists before L7. Reserve (L3) and init (L6) load no binding: reserve reads only
  the template fields of the running package's foundation (`cli.py:319-323`). The first binding happens at M2,
  after the re-pin (L4). The 1.0.0 initial root admits only its exact head, so step 6 uses P5-4's
  frozen-checkout replay rather than a documentation-only successor. Nothing on L1 to L7 needs a binding to
  survive a configuration change.
