### Major

#### R5-M1. The pin-advance comparison is skipped by the bypass every pin advance needs, runs against a base that moves, and is never re-run on the landed commit

- **Claim (note 679 to 687, 1364 to 1376, 1449, 1478):** pin advances are checked at pull-request time in the required `admission-controls` job, "on the merge queue it evaluates the exact squash candidate" (note 680), an unnamed verdict change "fails closed" (note 686), and the post-merge walk has no second tool (note 679).
- **Evidence:**
  1. *Every PR that runs the comparison is a bypass merge.* A pin advance appends a `baselines` row, so it changes `.research-system/evidence/w9/walk-baseline.json`, which Option I1 code-owns (the directory pattern, note 104, 737, 1531). The ruleset requires code-owner review with `required_approving_review_count: 0` (note 146 to 150), and its only bypass actor is the repository admin role in `pull_request` mode (live `GET rulesets/20822054`). `.github/CODEOWNERS:6-8` already says changes to owned files "need a deliberate admin bypass". The note says the same of this lane: "Requires Stephen's bypass merge (`Bypass reason:` ...) on every ... baseline/pin-advance, or closure-edit PR" (note 1532; also note 702). 32 of the 56 evaluations in the live month window are bypasses (note 1935). A bypass merge does not wait for required checks. So for the only PRs that run the comparison, a red `admission-controls` is a signal Stephen may read, not a block. Nowhere does the note say so.
  2. *The base is `origin/main` (note 683).* On `pull_request`, `HEAD` is GitHub's test-merge ref, built at an earlier main tip. On `push` to `main` (`ci.yml:4-5` triggers the whole workflow, so `admission-controls` runs there too) `origin/main` equals `HEAD`, so the trigger "`HEAD`'s blob map differs from `origin/main`'s last row" is false and the landed commit is never compared. The post-merge detector has one tool (note 679) and Rule 0.2 (v) is deleted (note 788). Nothing else compares.
  3. *Judged twice or never.* The candidate commit is judged by the old tool at PR time and by the new tool at PR time and after the merge. History in `(b0, P1]` is compared once, at PR time, against whichever base was current then. The landed commit, the one that matters, is compared by nothing. Rule 0 verdicts are never compared (R5-M2).
- **Failure scenario:** a pin-advance PR changes a rule so that an old violation at commit `V` becomes clean. The author leaves `V` out of the slice, or main moved after the last green run, or `admission-controls` fails for a reason unrelated to the change (R5-M3) and Stephen merges by bypass, his normal path for this PR. The post-merge detector runs only the new tool and is green. History has been re-judged silently, the case R2-M2 (b) existed to stop, and it left no red run on `main` to notice.
- **Impact:** the control's reliability rests on a human choosing to wait for a check in a lane the design says he bypasses, while §1, §6.1, MC-2 and claim 2 describe it as blocking. This is the property the old post-merge design (v) had (a bypass could not skip it) and revision 5 gave up.
- **Disposition:** fix now (design text, one test). No owner decision except the L-1 exit criterion below.
- **Proposed text:**
  - "The base of the comparison is `HEAD^1`, not `origin/main`. It runs when the last `baselines` row of `HEAD` differs from the last row of `HEAD^1`. On `pull_request` and `merge_group` `HEAD^1` is main's tip when the merge ref or queue entry was built; on `push` to `main` it is the previous main commit, so a bypass-merged pin advance is compared on the landed commit. A red push run is a signal, not a state: the repair is a follow-up PR that names the difference or reverts."
  - In §6.2.2 item 4, MC-2, claim 2 and HR-3: "A PR that appends a row touches a code-owned path and merges by bypass. Its PR-time result is advisory unless Stephen waits for green; the push run on the landed commit is the check that cannot be bypassed."
  - Add "the latest `admission-controls` push run on `main` is green" to the batch checklist (`06v:603-604`) and to the L-1 exit criteria.
- **Affected:** R2-M2 (b), R4-M1; note §6.1, §6.2.2 item 4, §10.3, §13.1 MC-2, §13.2 HR-3, §14 claim 2, Owner Points C and F.

- **Claim (note 684, 788, 1478, 1766; brief §2.2):** "Rule 0 is excluded from the compared verdict (preventing recursion)". The interval includes the candidate "so `origin/main`'s old tool also judges the candidate commit introducing the new tool" (note 683).
- **Evidence:**

None of those is under Rules 1 to 3, whose paths are `results/` outside `results/ars/`, registered legacy files and registered shared surfaces (note 799 to 817; the 22 guarded commits in note 575 are the `CONVENTIONS.md`, `results/`, `papers/`, `contracts/` and `.apm/` ones). A pin advance whose tool hard-codes `M` changes only the Rule 0.3 verdict at `M`, which the comparison ignores, so it needs no slice and leaves no hash-bound record. Every unit control in note 1415 uses synthetic repositories and designated cases, and passes. The comparison reports no difference. - **Impact:** R2-M2 (b), "a tool change cannot silently re-judge history", is not closed for the rules that guard the detector itself; the exit Stephen is asked to choose in Owner Point C has an unrecorded third form.

- **Proposed text:** "The verdict of commit `V` under tool `t` is the set of `(rule, path)` pairs for which `t` reports a violation at `V`, after the `acknowledged` rows present at the base. Rule 0 pairs are `("0.1", path)`, `("0.2", path)` and `("0.3", path)` and are compared. Rule 0.2 (v) does not exist, so nothing nests. A run that does not complete is `ERROR`." Add to HR-3 and Owner Point C: "A pin advance that exempts a commit is a verdict change at that commit and must be named in the slice. A Rule 0 difference that turns a historical commit red cannot be acknowledged (`acknowledged` covers Rules 1 to 3); it is refused in review unless Stephen picks the exemption row."
- **Affected:** R2-M2 (b), R4-M1 item 3; note §6.2.2 item 4, §6.5, §13.2 HR-3, §14 claim 2, §16.2.
