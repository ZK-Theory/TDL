### Minor

**m-1. The "no current binding" test is made once, outside the writer lock, and the binding service briefly removes
the pointer while it replaces it.**
- **Evidence:** `_foundation_binding_check` reads `os.path.lexists(pointer)` when `ars submit` starts (`cli.py:937`),
  before it builds the service or takes the lock. Its result, `None` or a `revalidate`, is fixed for the whole
  submission. The advance replaces the pointer through `DirectoryTransaction.replace_or_recover`. That unlinks the old
  final and then publishes the new one (`store/anchor.py:2732-2733`), under the advance's writer lock
  (`binding_service.py:1378`). The pointer is therefore absent for a moment, and also after an "absent-final" crash,
  which the same code anticipates (`:2713-2720`).
- **Probe:** `test_m1_the_skip_decision_is_taken_outside_the_lock_and_the_pointer_is_absent_mid_replace` replaces a
  scratch pointer through the real `LockedRoot.replace_exact_file`. At the publish step, `lexists` is `False` and
  `_foundation_binding_check` returns `None`, the never-bound answer.
- **Failure scenario:** an `ars submit` from the old checkout starts during the advance and reads the pointer in that
  window. It builds `CommandService(binding_check=None)`, waits on or retries the lock, and appends after the advance
  with no recheck. A grant-free `VerifyEvidenceDeletion` is not stopped by the grant fence. This is M-1's original
  failure, narrowed to a window. A process started during the advance breaks the drain ("none starts from it until
  the advance"), so today the drain discipline covers it. P-082 item 4, though, asks for a mechanical refusal.
- **Fix (in scope, `cli.py` only):** when the foundation names the store, always pass a binding check. Make that
  check decide inside the lock: if the pointer is absent there, return; if it is present, load and `revalidate`, or
  refuse with the same message. The early check can stay for the refuse-before-bind property. The alternative is to
  record the window as a known limit and keep the drain line.

**m-3. `inventory reproduce` never refuses an output under the vault, and `inventory build` refuses one only when it is
given `--vault-root`.**
- **Evidence:** note §12 says each tool "refuses an output path under `.apm/`, under the vault, or inside a store".
  `refuse_tool_output` checks the vault only when `vault_root` is given (`legacy/inventory.py:265`). Reproduce passes
  `vault_root=None` (`cli.py:1723`) and has no `--vault-root`. Build takes `--vault-root` as optional, for `vault_file`
  sources only. The PR's guard test skips the vault case for reproduce: "reproduce reads no vault, so names none"
  (`test_w9_wp9_3_inventory_builder.py:305`). The record does not list this as a reading.
- **Probes:** `test_m3_reproduce_writes_into_a_vault_it_is_never_told_about` writes a report into a scratch
  `TDA-Research/05-Daily/` and exits 0. `test_m3_an_output_through_the_repositorys_vault_junction_passes_both_guards`
  shows the repository's `vault/` junction resolving out of the repository. So without `--vault-root`, an output named
  `<repo>\vault\x.json` is neither "inside the repository it reads" nor "under the vault".
- **Failure scenario:** an operator runs `ars legacy inventory reproduce … --output vault\05-Daily\report.json` from
  the TDL checkout. The tool writes into the research vault, which §12 forbids.
- **Fix:** require `--vault-root` on both tools and always check it, or pin the vault path. The other option is to
  record that the tools cannot know the vault without being told. The `.apm/` guard has the same structure but needs no
  root, because it matches the name.

## 4. M-2's resolution against contract §3

- **`heading_section`:** a level-k heading outside every declared structural range. This matches `segment`'s item
  rule and R-3's reading (suppression at level k only). The resolution and `segment` use the same `_lines`, `level`
  and `_declared` helpers, so the 1-based to 0-based conversion and the structural bounds agree by construction.
- **`computational_log_entry`:** dated level-2 or level-3 headings, plus digit headings (m-2). A level-4 dated heading
  and a level-1 heading are not anchors. That is right: neither opens a row under `segment`.
- **The last line** is `len(_lines(data))`, which is right with and without a final terminator. The `after_line` hash
  splits on `\n` and so counts one more "line" when the file ends with a terminator. That line's hash is
  `sha256(b"")`, and the resolver then refuses the value as out of range. So the two line models cannot together admit
  a declaration.
- **The independent property** (`test_m2_independent_property_…`, seed 20261111, 3,000 files, more than 1,000
  resolved cases). The generator has duplicate anchors, nested and digit headings, dated level-4 headings, invalid
  UTF-8 headings, rules, CRLF, BOM and random structural ranges. Two checks hold on every case:
  - every whole-file item, `unparseable_anchor` or `duplicate_anchor` row that starts after `after_line` starts a
    resolved-region row with the same raw bytes;
  - LR-011 admits exactly the resolution and refuses the first line moved by one either way, and the last line moved
    back by one.

## 6. The T2 lock-race failure

`suite (8)` on `649d0698` (job 130102371594, Windows, Python 3.13.5) failed
`test_t2_authority_lock_revocation_wins_and_rechecks_authority[AuthorizeProviderIssue]` with `ConflictError('writer
lock name was replaced during exact generation deletion')`. It was 1 failure in 326 tests, in a 22-minute shard.

| Run | `649d0698` | `0ea4e489` |
|---|---|---|
| 40 fresh processes, both parameters (80 cases) | 0 failed | 0 failed |
| One process, 300 repeats × 2 parameters (600 cases) | **1 failed** (`AuthorizeProviderIssue`) | **3 failed** (all `AuthorizeProviderIssue`) |

Every failure carried the same message. The in-process runs ran at the same time as each other and as this review's
regression suite, so the machine was loaded, like a CI shard.

**Conclusion: a flake on both trees, not caused by #428.** It is also not caused by WP9.3-1's in-lock recheck:
- the test's `_service` passes no `binding_check`, so `_recheck_binding` is a no-op;
- `store/anchor.py` and the test are unchanged since 2026-09-11 and 2026-08-02.

The message comes from the writer lock's exact-generation deletion (`store/anchor.py:1727-1731`). After deleting its
lock file, the releaser re-checks the name and raises if a file is there. `AuthorizeProviderIssue` retries on
contention every 10 ms (`command/service.py:1915-1933`). So the likely sequence is:
1. the revoker deletes its lock;
2. the submitter's retry creates a new lock file at the same name;
3. the revoker's post-delete check sees it and raises.

That is a real property of `WriterLock` release under contention, not only of the test: a releaser can raise after
its locked work has finished. It is outside WP9.3's scope, and it is offered as a follow-up observation. Run logs are in
the session scratchpad; the commands are in §8.
