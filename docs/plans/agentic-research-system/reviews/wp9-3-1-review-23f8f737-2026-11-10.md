### Major

**M-1. `ars submit`'s in-lock binding recheck disappears exactly when the checkout is not admitted.** (Goes to
Stephen; it changes what note §9.1 and §18 claim.)
- **Evidence:** `research_system/cli.py`, `_foundation_binding_check`, returns `None` (no recheck) on any
  `IntegrityError` from `load_current_binding`. `ars submit` then builds `CommandService(binding_check=None)`. After
  an advance, the old checkout is refused with exactly that error: "current store binding identity is invalid", a
  `code_roots` mismatch (`store/current_binding.py:837-846`). A moved Git subject raises the same type (`:849-851`). The
  PR pins this behaviour as intended
  (`tests/research_system/integration/test_w9_wp9_3_writers.py:318-319`, "named, never bound").
- **Probe:** `test_m1_after_a_pin_advance_ars_submit_from_the_old_checkout_runs_with_no_recheck` runs on the PR's own
  v1.2 advance fixture (`_pin_intent`). Before the advance, `_foundation_binding_check` returns a recheck. After it,
  `load_current_binding` from the old checkout raises `IntegrityError`, and `_foundation_binding_check` returns
  `None`. 1 passed, 85 s.
- **Failure scenario:** a later W0 pin is released by advancing a store's binding (note §9.1). A process started
  after the advance from the old, pre-pin checkout runs `ars submit` with `VerifyEvidenceDeletion`. That command is
  grant-free, so the grant fence does not stop it, and it targets the candidate's derived `dec_`. The W9 and W11
  paths refuse such a checkout through the code-root check. The generic path gets no recheck, and its identity
  check holds the pre-pin constants. So it appends, and the first replay on pinned code then refuses the whole ledger.
  Recovery is an owner ruling. Note §9.1 says the opposite: "On WP9.3-1 code the `CommandService` recheck refuses
  it". So does §18's "refusal of a writer on pre-pin code".
- **Why it goes to Stephen:** the behaviour follows the implementer's reading of Stephen's 2026-11-09 option "Recheck
  if foundation-named", whose "tries" was taken to mean "no recheck if the binding does not load, for any reason"
  (record §3 item 3). The question for Stephen: did that option mean to cover an *unadmitted* checkout of a named
  store, or only a store that was never bound? The narrow fix keeps "never bound" as "no recheck", and refuses when
  the store has a current binding that this checkout fails to load. It needs his ruling, because it amends P-081
  item 3. Until then, a later pin's checklist must add "no generic `ars submit` from the old checkout after the
  advance" to the drain.

**M-2. LR-011 does not check how a "from the first anchor after" region is resolved.**
- **Evidence:** `research_system/legacy/preparers.py`, `check_resegmentation`, `:255-265`. For
  `form: first_anchor_after` it checks only `after_line_sha256`, then re-segments over the declared
  `resolved_first_line` and `resolved_last_line` (`_segment_kwargs`, `:222-223`). Nothing checks that
  `resolved_first_line` is the first anchor after `after_line`, or that `resolved_last_line` is the end of the file.
  Replay cannot check either, because the bytes are not in the ledger. Contract §3 makes the resolution the
  inventory's job, and the LR-011 preparer is where the inventory is checked.
- **Probe:** `test_m2_a_wrong_resolution_of_first_anchor_after_is_admitted`, with three cases: one skips the first
  anchor, one stops before the end, one does both. In each, the check passes, and an item that is in the declared
  region is missing from the rows. The controls show the true resolution admitted and a wrong `after_line` hash
  refused. 6 passed with the other fast probes.
- **Failure scenario:** an inventory declares "from the first anchor after line 22" but resolves to lines 40 to 300.
  Every item in lines 23 to 39, and after line 300, drops out, blockers included. The record still claims the
  "first anchor after" form. The LR-013 reproducer re-segments over the same declared range, so it reproduces the
  omission rather than catching it. Note §6.2 says "so no blocker row is dropped".
- **Fix:** in the preparer, derive the resolution from the bytes and require it to equal the declared lines: the first
  non-suppressed anchor line after `after_line` for the selector, and the last line of the file. Add a negative
  control for each wrong resolution.
