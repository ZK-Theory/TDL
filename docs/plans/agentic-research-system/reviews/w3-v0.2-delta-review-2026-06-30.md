## 3. Dimensional and lifecycle checks

Task Observer Observation 9 was applied explicitly.

### 3.1 Token dimensions

The candidate does not compare raw counts from different tokenizers. It enforces:

```text
reference-token count <= W3 profile ceiling
bound-provider token count <= floor(0.80 × provider usable input capacity)
```

The manifest records both tokenizer/count identities, or the evaluated provider upper-bound identity. Section 16 blocks issuance if provider accounting is unavailable or either gate fails. F-028 exercises both failure paths.

### 3.2 Lifecycle order

The state order remains:

```text
requested -> compiling -> compiled -> validated -> issued -> delivered
```

Section 10.1 now matches it: deterministic bytes/hash exist at `compiled`; W4/W7 route and count before `validated`; issuance follows all validation; delivery follows issuance and requires a matching content-hash receipt. A failed provider route remains an explicit unissued candidate outcome.

## 6. Practicality and residual risks

- R0 retains one manifest schema but only a manifest reference is model-visible by default; operational overhead must be measured before introducing a variant.
- Provider counting remains dependent on W7 delivering an exact tokenizer or evaluated conservative upper bound. A route without either is deliberately unusable.
- The 48,000/32,000 reference ceilings remain provisional until F-025/F-026/F-021/F-022 measure real mandatory closure. Fail-closed behavior makes an infeasible profile blocking rather than unsafe.
- Delta-review exposure remains an independence reduction and must be materialized as a narrow W4/W5 policy with attributed use.

These are explicit downstream gates, not unresolved contradictions in the written W3 interface.
