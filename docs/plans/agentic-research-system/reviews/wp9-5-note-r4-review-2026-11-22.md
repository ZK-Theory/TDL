### Major

#### R4-M1. The pin-advance verdict comparison (Rule 0.2 (v)) cannot be implemented or bounded from the note

- **Claim (note 728-736, 856, 1601):** for each `baselines[k]`, `k >= 1`, the detector assembles `baselines[k-1]`'s tool, walks `(baselines[0]["baseline_commit"], P1(C_k)]` under both tools, compares each commit's `(rule, path, outcome)` tuple, and fails with `ERROR: ... Rule 0: pin advance changes verdicts` unless every differing commit is named (`V[:8]`) in the row's decision slice; "recomputed on every run"; "each pin advance adds one re-walk" (note 736); 23.11 s measured (note 736, 1552, 1991).
- **Evidence:**
  1. *Verdict undefined (note 732, 856).* Nothing says what `outcome` ranges over, whether Rule 0 (and so (v) itself) is part of the tuple, how `acknowledged` rows are applied (those at head, or those at `P1(C_k)`), or what an old tool contributes when it does not complete (`ImportError`, exit 2 from an API failure, timeout). If a crash is read as "no violations", a broken old tool is indistinguishable from a green one. "Named" is a substring match of `V[:8]` anywhere in the slice, so one mention excuses every tuple change in that commit.
  2. *Recursion.* (v) is a clause of Rule 0.2, which each tool applies to every commit it walks, including the earlier commits that appended rows. Unless results are memoised per (blob-map digest, commit), which the note does not say, the cost obeys `S_k = 3 S_{k-1} + 2 N_k b`. With `b = 0.069 s` (the note's figure) and `N_k = 80 k` commits, `S_8` is about 15 hours (`r4_walk_cost.py`).
  3. *Interval excludes `C_k`.* (v) stops at `P1(C_k)` (note 732, 856). The commit that introduces tool `k` is judged only by tool `k`: the commit being judged supplies the tool that judges it, for exactly the commit where the tool changes. A regression or weakening in tool `k` that turns `C_k`'s own Rule 0 to 3 verdict green is outside every check except the human merge. The same applies to `detector-controls.json`, which tool `k` records.
  4. *Invocation.* The nested walks need `--head P1(C_k)` and an "active row" (row `k` is not yet in the file at `P1(C_k)`). §6.3 item 4 (note 780, 714) makes `--head` exit 2 unless `--ruleset-check skip`. The note does not say the nested call passes it, and does not require every historical tool version to accept the same command line.
  5. *Cost.* The 23.11 s figure is two `git` subprocesses per commit (`rev-parse`, `diff-tree`) over the 320 commits of `4b143c92..dbd54fe3`. I reproduce it: 21.95 s, 0.069 s per commit. That is Option C2's interval; under the recommended C1 the walked interval starts at `baselines[0]["baseline_commit"] >= dbd54fe3` (note 709). A six-subprocess stand-in (adding `walk-baseline.json` and `registration-manifest.json` reads at `P1` and `C`) takes 65.3 s, 0.204 s per commit, and the real walk adds a `gh api` call per guarded commit. The design makes `1 + 2K` walks per run, not "one re-walk" per advance. With 59 first-parent commits a month (178 in 90 days) and the note's own closure-edit rate (14 in 90 days, note 750), per-run evaluations are about 2.6k at 3 months, 10k at 6 and 40k at 12: 3.0, 11.7 and 45.8 minutes at 0.069 s per commit, 9.0, 34.7 and 136 minutes at 0.204 s. The workflow has `timeout-minutes: 15` (note 1334). Rows are append-only and checkpoints are gone, so the only off-ramp is raising the timeout, which is itself a closure edit.
- **Failure scenario:** an implementer follows the text. Either the nested walks re-apply (v) and the run does not finish by the sixth advance, or the implementer picks verdict semantics the note never reviewed, and the required negative control ("a pin advance that turns a red commit green, not named in the slice, fails") cannot be written without a verdict definition. Separately, tool `k` merges with a defect that passes its own commit.
- **Impact:** R2-M2 (b), the control that stops a tool change silently re-judging history, is neither testable nor bounded; the detector eventually stops finishing.
- **Disposition:** fix now (design text, tests, UNVERIFIED entry); the cost placement is an owner choice under Point C.
- **Proposed text:**
  - "The verdict of commit `V` under tool `t` is the set of `(rule, path)` pairs for which `t` reports a violation at `V`, after applying the `acknowledged` rows present at `P1(C_k)`. A run that does not complete is `ERROR`, never the empty set. Rule 0 is not part of the compared verdict; (v) is evaluated once per row, and per-run results are memoised on `(blob-map digest, commit)`."
  - "The comparison covers `(baselines[0]["baseline_commit"], C_k]`, so tool `k-1` judges `C_k` too."
  - "Nested calls use `check_legacy_writes.py --ruleset-check skip --head <rev> --active-row <k>`; every tool version keeps that interface, and a pin advance that changes it says so in its slice."
  - Cost, either (a) state the measured full-walk time with the real rules and PR mapping and a stop rule that returns to Stephen when a full run exceeds a stated wall time, or (b) recompute (v) for the newest row on every push and for all rows in a weekly scheduled run and in the operator wrapper. Nothing is stored in (b); every figure is still recomputed from scratch.
  - Add "full-walk wall time with real rules, PR mapping and K = 5, 10, 20 rows" to §21.2 and §15.1.
- **Affected:** R2-M2, R3-M2; note §6.2.2 item 4, §6.5 Rule 0.2 (v), §12.1, §12.3, §21.1 item 10, Owner Point C.

#### R4-M2. A closure edit that lands without its row is unrecoverable, and the routine path to it has no pre-merge check

- **Claim (note 748, 863, 1573, 1601):** closure edits are preventive for code-owned paths and detective for the rest; Rule 0.3 detects an unrowed edit post-merge, and "an unrecorded closure edit requires Stephen's intervention / revert".
- **Evidence:**
  1. *No exit.* Rule 0.3 is evaluated at the editing commit (note 863). The walk always restarts at `baselines[0]["baseline_commit"]` and re-walks in full (note 709, 729), and that start is immutable (note 709). `acknowledged` covers Rules 1 to 3 only (note 748). A revert needs its own rollback row and leaves the original commit `M` in the walked interval. No re-baseline mechanism exists (grep). The only mechanical exit is a pin advance whose tool hard-codes an exemption for `M`, which the note does not provide. This is the failure R3-M1 evidence 2 described, on the other branch of the protocol.
  2. *Pre-merge coverage is indirect and partial.* The PR-lane tests are `test_recorded_detector_import_closure_covers_ast_walk`, which compares module paths, not blobs (note 746), and, under `L1_LIVE`, `--verify-watched-to-fail` on `detector-controls.json` (note 1472, 1301). The second fires only for modules in some detector's import closure, because transcripts bind `closure_blobs`. It forces such a PR to re-record a code-owned file, but never checks that a `baselines` row was appended. Not covered at all: `pyproject.toml` and `uv.lock` (in the pin, note 661-662, 1655; not code-owned; in no transcript), and any bypass or direct-push merge.
  3. *Frequency.* 14 of 178 first-parent commits in 90 days touched the 15 existing closure modules, 7 in the last 4 weeks (note 750; I reproduced both). `pyproject.toml` or `uv.lock` was touched by `ddf1da77` (2026-10-06) in the same window.
- **Failure scenario:** after L-1, a PR adds a dependency to `pyproject.toml` and `uv.lock` for a research analysis. No required check covers either path, so it merges green. On the next run Rule 0.3 fails at that commit, and on every run after. No sequence of PRs clears it. A second scenario: a PR that edits `research_system/legacy/reader.py` re-records `detector-controls.json` (so the PR-lane tripwire passes and Stephen's code-owner review is triggered) but forgets the row.
- **Impact:** operational bypass: the permanently-red outcome R1-M5, R2-M2 and R3-M1 each named, and loss of the detector.
- **Disposition:** fix now (a) and (b); (c) is an owner decision.
- **Proposed text:**
  - (a) "In `admission-controls` (Option F1), when `L1_LIVE`, `test_w9_detectors.py` asserts for the checked-out tree, which on `merge_group` is the candidate: for every path in `baselines[-1]["detector_closure_blobs"]`, the recorded blob equals `git rev-parse HEAD:<path>`; and Rule 0.2 (i) to (iv) hold for every row appended since `origin/main`." It runs in under a second, needs no ruleset change, and makes Rule 0.3 preventive for all 25 paths except under bypass.
  - (b) Decide whether `pyproject.toml` and `uv.lock` belong in the pin at all (R4-m7: the existing closure imports only the standard library).
  - (c) Put to Stephen under Point C: either a narrowly scoped, hash-bound exemption for a Rule 0.3 miss (tuple `(commit, path, old_blob, new_blob)` plus a decision slice, as for `acknowledged`), or accept permanence and list it in §13.2. Reword note 748, MC-2 and claim 2 to say which.
- **Affected:** R3-M1; note §6.2.3 item 3, §6.5 Rule 0.3, §10.3, §13.1 MC-2, §14 claim 2, Owner Points C and I.
