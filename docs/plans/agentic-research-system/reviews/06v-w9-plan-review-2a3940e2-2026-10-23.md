## 4. Findings

### Major

#### M-1. The shared-ledger replay seam is not mapped, and an unpartitioned W9 event breaks the store

- **Claim.** 06v §2.1 says W9 "does not touch W11's route partition, its excluded rows or its schema tree", and D-2
  says the Discovery-style package keeps W9 out of protected code. Both are true but beside the point. A W9 runtime
  that appends to the same ledger as Discovery must be recognised by every whole-ledger replay in that store, and
  06v maps none of them.
- **Evidence.**
  - `research_system/projection/replay.py:1319-1324` treats an event as Discovery's only when
    `is_discovery_projection_event` holds. That predicate is closed over `DISCOVERY_COMMAND_TYPES`
    (`research_system/discovery/commands.py:14-44,84`). Every other event goes to `apply_event`, which ends with
    `raise IntegrityError(f"unsupported event type: {event_type}")` at `replay.py:1125`.
  - `research_system/discovery/routes.py:301-319`: `shared_event_partition` sends any event type it does not know to
    `"operational"`, which `replay_discovery` hands to `replay_control_plane`
    (`research_system/discovery/replay/driver.py:396-400,695-698`).
  - `DiscoveryRuntime` replays the whole ledger before every Discovery command (`runtime.py:474-483`, raising
    `DiscoveryLedgerReplayError`). `replay_discovery` first runs `_replay_shared_partitions` over the whole ledger
    (`driver.py:66-75`).
  - Discovery appends under a three-root `CompositeWriterLock` (`runtime.py:194-198`). 06v names no lock for the W9
    runtime.
- **Failure scenario.** L-3 writes `W9CatalogueGenesisImported` into the Gate 7 store, which already holds an
  irreversible W11 genesis (L-2). From then on, `ars projection rebuild` fails with "unsupported event type". Every
  Discovery command fails replay before preparation. Backup verification and restore replay may fail the same way.
  The store is unusable for W11 and for successor compute, and it cannot be rolled back.
- **Impact.** Operations and migration. WP9.2's own scratch-store tests would probably catch this, but the fix
  would then be improvised inside a package. It could touch `discovery/routes.py` and `projection/replay.py`, which
  are code W11 and WP6 own, and none of the §8 stop rules covers that.
- **Disposition.** Fix now, in 06v.
- **Required change.** Add a §2.2 row "Shared-ledger replay", citing `projection/replay.py:1125,1319-1324,1369-1381`,
  `discovery/routes.py:301-319`, `discovery/commands.py:84` and `discovery/replay/driver.py:66-75,396-400`. In WP9.2,
  add:
  - a `legacy` command-type predicate, owned by `research_system/legacy/`, that `projection/replay.py` and
    `shared_event_partition` consult before their defaults;
  - a lazy `replay_legacy` call at the generic boundary, next to the `replay_discovery` call at
    `replay.py:1369-1381`;
  - the same three-root `CompositeWriterLock` as Discovery;
  - a test: a scratch store holding W11 genesis, W9 genesis, one W9 observation and one generic command must replay
    through `rebuild_projection`, `replay_discovery` and the verify-restore path. The negative control is the same
    ledger with the predicate removed, which must fail.

  State that editing `shared_event_partition` is in scope and leaves the 59/21/1 partition unchanged, or add it to
  §2.6 as U-5 with "stop and return Partial" if the edit cannot be confined to a predicate.
- **Affects.** D-2, WP9.2, L-2, L-3, the §8 stop rules.

#### M-2. U-1 is already answerable from the code, and the answer changes D-4

- **Claim.** U-1 (06v:100) asks whether W9 commands can bind to `ars://core/command` 1.0.0 without new
  `_RUNTIME_BINDINGS` rows, "if it can, the census count may stay at 261". It cannot.
- **Evidence.** Every Discovery command has its own row: `SchemaBinding("ars://core/command", "1.0.0",
  command_type="…")`, at `research_system/schema_registry.py:209-265`. `command_binding` is keyed by command type

  command binding" at `cli.py:1206-1208`. Events need no row: `event_schema` falls back to `ars://core/event` 1.0.0
  (`runtime.py:588-613`).

  discharge relation, citation status), WP9.6 (supersession, recovery, manual-mode events) and probably WP9.3
  (observation and acceptance commands) add more. D-4 has Stephen re-accept the protected identities only "at WP9.2's
  PR review". Every later package then either changes a P-059 pin without re-acceptance, which is a §8 stop rule, or
  the stop fires in every package with no procedure behind it.
- **Impact.** Authority (P-059) and operations.
- **Disposition.** Fix now.
- **Required change.** Replace U-1 with a §2.2 fact: "each W9 command type needs one `_RUNTIME_BINDINGS` row
  (`schema_registry.py:209-265,1547-1549`; `runtime.py:205-207`; `cli.py:1206-1208`); events fall back to
  `ars://core/event` 1.0.0 (`runtime.py:588-613`). The census changes in every package that adds a command." Then
  either (a) WP9.2 adds the rows for every command in the accepted W9 catalogue at once, with grants refused for any
  command whose handler has not landed, or (b) D-4 applies at every package that adds a command. Name the 06h
  manifest file (`tests/research_system/smoke/wp6_1_06h_current_append_manifest.yaml`) as one of the re-accepted
  bytes.
- **Affects.** U-1, D-4, O-6, WP9.2 to WP9.7.

#### M-3. The successor-side guards live in the generic W2 command service, and 06v maps none of their seams

- **Claim.** D-2 says the Discovery-style path "keeps W9 out of the `core/commands` and `core/events` protected
  trees". That holds for the legacy commands. It does not hold for the guards in W9-T8, T10, T11, T12, T16 and the W5
  clause of T17. Those guards act on successor objects that the generic service owns, and only T12 has an
  interface-unverified entry (U-2).
- **Evidence.**
  - W9-T8 refuses "an unadopted closed-reference family in a successor Task". A Task names its sources through
    `CreateTask`'s `definition.source_import_refs` and `portfolio_refs`
    (`.research-system/schemas/core/commands/create_task.schema.json:264,314`). That schema is in the protected
    `core/commands` tree (`wp6_2_t2_expectations.py:406-409`). The refusal belongs in the CreateTask preparer in
    `research_system/command/service.py`, not in `research_system/legacy/`.
  - W9-T10 refuses "a successor Task writing a legacy path or legacy pre-registration". The Task definition has no
    output-path field (same schema: `expected_artefact_types`, `root_binding_requirements`), so outputs reach the
    ledger through `RegisterArtefact`. 06v's "declared outputs and pre-registration paths" (06v:371) name a field that
    does not exist.
  - W9-T11's first clause, "Register a `*.pkl` or null cache as an ARS artefact … rejected", is a guard on the
    generic `RegisterArtefact` path. Nothing in `research_system/` refuses restricted bytes today: the grep for
    `\.pkl|restricted|UKDA` finds only unrelated hits (`artefacts/use_resolver.py:273` is about consumers;
    `context/sources.py:83-89` about context sources). 06v's WP9.2 "store half" covers only the legacy observation
    record.
  - W9-T17's last sentence, "A family marked unadopted blocks its claims in W5", needs a hook in the W5 assurance
    engine. 06v names none.
- **Failure scenario.** WP9.4 or WP9.7 has an implementer discover that the guard must edit `command/service.py`
  and, for T8 or T10, possibly a core command schema. Either the guard is weakened to fit the legacy package, which
  produces the hollow binding that memory `feedback_escalate_into_rework_plan` warns about, or a protected tree
  changes without a planned re-acceptance.
- **Impact.** Validity of W9-T8/T10/T11/T17 and P-059 authority.
- **Disposition.** Fix now.
- **Required change.** Add a §2.7 "Successor-side seams" table. Give each of T8, T10, T11 (artefact clause), T12,
  T16 and T17 (W5 clause) the owning module and line, the field it reads, and whether a schema in `core/commands` or
  `core/events` must change. Add U-5 to U-7 for the ones that cannot be settled by reading (the W5 hook, the T10
  output field). Say that if any protected tree changes, D-4 covers it. Reword D-2's rationale to "keeps the legacy

- **Affects.** D-2, D-4, O-22, O-23, O-24, WP9.4, WP9.7.
